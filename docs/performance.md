# Performance and reproducibility

TimeTuck's original motivation includes investigating whether native Rust can
deliver Timefold-style planning capabilities with strong performance. The
repository includes matched Java/Rust experiments and recorded wins on particular
workloads. It does not establish an application-independent speed advantage.

## What the existing results establish

| Evidence | Interpretation |
| --- | --- |
| Original native acceptance cohort | A retained qualification reached the project's 109 measured time/quality targets across 18 comparison jobs. This is a bounded historical acceptance result, not a universal speed claim. |
| Additional real-world applications | Two approved public workloads exercise actual Community streams and the native model. Historical arena revision d466 recorded Golfer 1.603× Java evaluations/s and Sailing 0.874×; both predate the Java occupancy-filter and native cooling fixes and are [superseded](../benchmarks/real_world/README.md#superseded-comparisons). The corrected default matrix with all four runtimes (input `e1b0c30a`, dedicated benchmark host, CPUs 2–3) qualified on 2026-10-22: streams Golfer 1.713× and Sailing 0.853× Java evaluations/s, one of two throughput targets met; handwritten incremental scorers Golfer 2.546× and Sailing 0.823×. All 24 outputs validate; every runtime was feasible on all Golfer runs and 2/3 Sailing runs. |
| Native optimization experiments | Paired native controls measure changes against a particular native baseline. These gains cannot be added to old Java/Rust ratios or treated as fresh Java comparisons. |
| Score and collector microbenchmarks | Operation-specific costs under defined inputs; they do not measure complete solver speed or final solution quality. |

See [completion evidence](completion.md), the [current implementation handoff](next-session.md),
and [dashboard methodology](dashboard.md) for the source-specific records. A retained
observation may refer to raw output in ignored local `work/` directories. That
output is not included in a fresh clone; rerun the named comparison when raw
samples are needed. This documentation pass does not refresh timings or assert
that older measurements are current.

## Compare the right quantities

For each application, report elapsed solve time, final hard/soft score, feasibility,
and relevant work counts together. Evaluations per second and solution quality
answer different questions. A faster candidate loop may explore a different
neighborhood or return a worse result under a fixed time limit.

Keep input data, initial states, pins, objective, and termination explicit. Use
same-machine serial pairs and rotating runtime order where the runner supports
them. Record compiler/JVM versions, build profile, affinity, seeds, warmup, raw
samples, and source/artifact hashes. Equal numeric seeds do not imply equivalent
random draws or search traces.

Small timing differences may be noise. Distinguish startup, compilation, warmup,
and measured solve work. Cross-machine results require separate interpretation.
An exhausted exact optimum, a quality threshold, and raw heuristic scores must be
labeled according to what was actually checked.

## Reproduce one comparison

Run only the comparison relevant to the question. These commands launch real
development builds and measurements; some can take minutes.

The Java adapters use pinned Community Maven artifacts. Install a suitable JDK
(the scripts require JDK 21 or newer; retained qualifications identify the exact
JDK used) and allow access to Maven Central. The ordinary Rust library needs
neither. See the [adapter protocols](../compat/oracle/README.md).

For example, from the repository root:

```sh
python3 scripts/differential_scores.py
python3 scripts/benchmark_scores.py
```

The differential run checks the named score arithmetic cases; the benchmark
measures its own score-operation workloads. To investigate a different area, use
the corresponding runner from [dashboard comparison documentation](dashboard.md).

For additional real-world workloads, follow the [application benchmark guide](../benchmarks/real_world/README.md),
including its pinned dependency setup and default matrix. A short diagnostic run
does not qualify the complete matrix. The handwritten Java incremental scorer is
a separate comparator from the actual Community streams engine.

## Preserve evidence

Measurements and generated reports live in ignored `work/` and `dashboard/data/`.
Keep timestamps, raw samples, and the source/configuration hashes generated by
the runner. Source changes can invalidate evidence; do not edit old hashes to make
it appear current. The local dashboard checks source freshness without running
measurements itself.

Safe public wording names the workload, source, machine, configuration, measured
quantity, and quality checks. “Faster than Timefold” without those boundaries is
not supported by the current evidence.
